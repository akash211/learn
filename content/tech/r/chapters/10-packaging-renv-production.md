# Packaging, renv and Production Caution

R code that runs on one analyst's laptop and R code that runs unattended every Monday are different
artefacts. The gap is not talent; it is version control of the *environment*, an explicit dependency
list, and an honest assessment of what R is good at when nobody is watching.

This chapter covers the mechanics — packages, `renv`, containers — and the judgement: where R is a
strong production choice and where it is the wrong tool.

## A package is the unit of reuse

If code is used more than twice, make it a package. It sounds heavy; it takes twenty minutes and
pays for itself the first time you need to test it.

```r
usethis::create_package("revtools")
usethis::use_r("revenue")          # R/revenue.R
usethis::use_test("revenue")       # tests/testthat/test-revenue.R
usethis::use_package("dplyr")      # adds to Imports in DESCRIPTION
devtools::document()               # roxygen comments -> man/ and NAMESPACE
devtools::check()                  # R CMD check
```

`DESCRIPTION` lists dependencies in three fields, and the distinctions are not decorative:

| Field | Meaning | Use for |
|---|---|---|
| `Imports` | must be installed; functions available via `::` | almost everything |
| `Depends` | attached for the user (`library(pkg)` loads it) | almost nothing; `R >= 4.1` |
| `Suggests` | optional; used in tests, vignettes, examples | test-only and optional features |

`NAMESPACE` is generated by roxygen2 from `@importFrom`/`@import` tags. Write `pkg::fun()` in
package code rather than relying on `library()` at the top of a file: a package cannot assume the
user's search path, and `::` is explicit at the call site. The one exception is `%>%`-style operators,
which need an import.

R CMD check is stricter than most people expect and it is right to be: it catches undocumented
arguments, global variables used in tidy-eval code (declare with `utils::globalVariables()`),
non-ASCII characters in code, and examples that fail. A package that passes `--as-cran` with no
notes is a package you can hand to someone else.

`testthat` (3rd edition) is the testing framework:

```r
test_that("revenue excludes refunds", {
  df <- tibble(amount = c(100, -20, 50), type = c("sale", "refund", "sale"))
  expect_equal(total_revenue(df), 150)
  expect_snapshot(summarise_revenue(df))
})
```

`expect_equal()` is tolerant of floating point; `expect_identical()` is not. `expect_snapshot()`
captures printed output so that changes to a report or a message are visible in the diff. `vdiffr`
does the same for plots. `covr::package_coverage()` tells you what is untested, which is usually the
error branch.

## renv: pin the environment, not just the code

`renv` records exact package versions in `renv.lock` and restores them.

```r
renv::init()        # creates renv/, renv.lock, and edits .Rprofile
renv::snapshot()    # write current library versions into the lockfile
renv::restore()     # install exactly what the lockfile says
renv::status()      # what is out of sync
```

The lockfile is JSON and belongs in version control. `renv/activate.R` is sourced from `.Rprofile`,
so opening the project in a fresh session activates the project library — that is the mechanism, and
it is why committing `.Rprofile` matters.

What `renv` solves: "it worked in March". What it does not solve: the R version itself (record it in
`renv.lock`'s `R.Version` and pin the interpreter in the image), system libraries (`libcurl`,
`libxml2`, `libpq` — those are Dockerfile lines), or data drift.

Practical notes:

- The `renv` cache (`~/.cache/R/renv` on Linux) shares packages between projects, so ten projects
  pinned to the same `dplyr` cost one install.
- `renv::snapshot(type = "explicit")` records only what `DESCRIPTION` declares, which is what you
  want for a package; the default `"implicit"` records everything in the library, including things
  you loaded once to check something.
- `renv::restore()` in CI is slow the first time and fast afterwards if the cache persists.
- Bioconductor projects need `renv::init(bioconductor = TRUE)` so the Bioconductor version is pinned
  alongside CRAN.

### Faster installs, and pinned CRAN

`pak` is a much faster installer (`pak::pak("tidyverse")`) with parallel downloads and better
dependency resolution; it is what `renv` uses internally when available.

For Linux, CRAN source packages compile for minutes each. Posit Package Manager serves **binary**
packages for common distributions:

```r
options(repos = c(PPM = "https://packagemanager.posit.co/cran/__linux__/jammy/latest"))
options(HTTPUserAgent = sprintf(
  "R/%s R (%s)", getRversion(),
  paste(getRversion(), R.version["platform"], R.version["arch"], R.version["os"])
))
```

The `HTTPUserAgent` line is not optional — PPM uses it to decide which binary to serve, and without
it you silently get sources. Setting a **dated** snapshot URL
(`.../cran/__linux__/jammy/2024-06-01`) instead of `latest` is the cheap way to make installs
reproducible without a lockfile; note that MRAN, the old Microsoft mirror, was retired in 2023, so
PPM snapshots are now the practical route.

## Deployment shapes

R runs in production in four shapes, in descending order of how well it fits the language:

1. **Scheduled batch.** `Rscript job.R` from cron, Airflow's `BashOperator`, a Kubernetes CronJob.
   Read, transform, write, exit. This is R's home turf: one process, bounded memory, no concurrency.
2. **Rendered reports.** Quarto/R Markdown on a schedule, published to a share or a bucket. Same
   shape as batch, with a template.
3. **APIs.** `plumber` turns annotated functions into HTTP endpoints:

   ```r
   #* Return revenue for a customer
   #* @param id:int
   #* @get /revenue/<id:int>
   function(id) {
     list(revenue = lookup(as.integer(id)))
   }
   ```

   `pr <- plumber::pr("api.R"); pr$run(port = 8000)`. This works, and plumber is used in production
   — but a single-threaded R process serving a scored model is a different reliability proposition
   from a Go or Python service, and `pr$run()`'s default is not a production server (`plumber` behind
   `nginx`, or Posit Connect, is).
4. **Shiny applications.** Interactive dashboards, where R's strength (analysis in the same process)
   is the point. Scale with `future`/`promises` for slow operations, `bindCache()` for repeated
   queries, and `bslib` for theming; test with `shinytest2`. Shiny Server, Posit Connect or
   `shinyapps.io` handle the operational side. A Shiny app is a single-threaded R session per
   process, so concurrency means processes.

Containers are the standard answer to "which R, which packages, which system libraries":

```dockerfile
FROM rocker/r-ver:4.4.1
RUN apt-get update && apt-get install -y --no-install-recommends \
      libcurl4-openssl-dev libxml2-dev libssl-dev libpq-dev \
    && rm -rf /var/lib/apt/lists/*
COPY renv.lock renv.lock
COPY renv/activate.R renv/activate.R
RUN R -e 'renv::restore()'
COPY . .
CMD ["Rscript", "job.R"]
```

`rocker/r-ver` pins the interpreter; `rocker/tidyverse` adds the meta-package (large, convenient);
`rocker/shiny` and `rocker/rstudio` are the other commonly used bases.

## Production caution, stated plainly

R is excellent at: statistical inference, exploratory analysis, reporting, time series and
econometrics, genomics (Bioconductor), spatial analysis (`sf`), and anything where a statistician
writes the code and the output is a document or a model.

R is weaker at: long-running services, high-throughput APIs, anything needing fine-grained memory
control, deep learning (the ecosystem exists but Python dominates), and integration into a
Python-or-Java data platform where the same pipeline already runs. The language is
single-threaded, everything lives in RAM, and there is no static typing — `sapply()` returning a
list where you expected a vector is a class of bug that a compiler would have caught.

The honest comparison with Python, which is the decision most teams actually face:

- **R wins** on the formula interface, the breadth of CRAN's statistical methods, `data.table`'s
  grouped performance, `ggplot2`'s grammar, Quarto/R Markdown for analysis documents, and
  `lme4`/`survival`/`emmeans`/`forecast` — packages with no equally mature Python equivalent.
- **Python wins** on engineering: packaging, CI, type checking, web frameworks, deployment,
  hiring pool, and the ML ecosystem. `pandas`/`polars` plus `statsmodels` cover most of what R does
  for tabular work; `scikit-learn` covers modelling breadth that R's `tidymodels` is still catching
  up to.
- **Neither wins on speed** in the abstract. `data.table` is competitive with `polars`; `pandas` is
  slower than both in many grouped operations; all three are fast enough that the bottleneck is
  usually the database.

Choose on the deliverable and the team, not on a benchmark. If the output is a statistical report
and the authors are statisticians, R shortens the path. If the output is a service that a dozen
engineers maintain, Python does.

## Common mistakes

- `library()` calls scattered through scripts with no dependency declaration; the code works only
  on the machine where everything happened to be installed.
- `install.packages()` inside a script — installs at runtime are non-reproducible and unsafe.
- Committing `renv.lock` but not `.Rprofile`/`renv/activate.R`, so the lockfile is never used.
- `renv::snapshot()` after loading twenty exploratory packages, pinning 200 dependencies for a job
  that needs six.
- Writing to `options()` or calling `set.seed()` at the top of a package function, changing global
  state for the caller.
- Catching errors with `tryCatch(..., error = function(e) NULL)` and continuing, which turns a
  failure into a silent zero.
- Assuming `Rscript job.R` exits non-zero on error. It does — but only if the error is not caught
  and swallowed.
- Deploying a Shiny app with an expensive query on initial load and no `bindCache()`.

## Production notes

The pattern that survives contact with operations: a container built from a lockfile, a batch entry
point that reads inputs, asserts their shape, writes outputs atomically, logs what it did, and exits
non-zero on any failure. Reports render from the same image.

```r
main <- function() {
  log <- logger::layout_glue_generator(format = "{level} [{time}] {msg}")
  logger::log_layout(log)
  logger::log_info("start")
  data <- read_input(Sys.getenv("INPUT_PATH"))
  stopifnot(nrow(data) > 0, !anyNA(data$id))
  result <- transform(data)
  write_output(result, Sys.getenv("OUTPUT_PATH"))   # write temp, then rename
  logger::log_info("wrote {nrow(result)} rows")
}
```

Atomic writes matter more than they look: a consumer that reads a half-written CSV sees a truncated
file and reports a 40% revenue drop. Write to `path.tmp`, then `file.rename()` — the rename is atomic
on the same filesystem.

And log the counts. "Wrote 1,204,331 rows, 12 rejected" is a log line that catches problems; "done"
is a log line that hides them.
