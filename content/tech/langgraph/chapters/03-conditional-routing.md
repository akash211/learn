# Conditional Edges and Routing

A conditional edge decides what should run after a node finishes. In LangGraph, the routing function receives current state and returns the next node name, `END`, a list of destinations, or `Send` values for dynamic fan-out. You can optionally provide a mapping from route labels to registered node names. This separates a decision from the work it triggers: one function chooses a path; the destination node performs it.

Use `add_conditional_edges(source, router, path_map)` when routing is naturally expressed as a pure decision about the resulting state. A clear router validates a small set of possible outputs and returns a known label. A static edge is better when the destination is unconditional. Use `Command` from a node when a single operation must both update state and select the next node. Avoid configuring both a static outgoing edge and `Command` routing from the same node: the static transition still runs and can create surprising extra work.

## Route by stable labels, not model prose

LLM output is probabilistic and can be malformed, incomplete, or adversarially influenced. If a model is used to classify a request, constrain the expected labels (for example, `"retrieve"`, `"answer"`, or `"clarify"`), validate the result, and map only those labels to known destinations. If validation fails, choose an explicit fallback or fail safely. Never use arbitrary generated text as a dynamic node name, URL, tool identifier, or authorization decision.

One design is for a model node to update `intent`, followed by a routing function that checks the value. Another is for a node to return `Command(update=..., goto=...)` when the classification result and route are tightly coupled. The former makes state and edge transitions separately observable; the latter keeps a local decision and update together. Prefer the simpler form that makes the graph easiest to inspect and test.

```python
from typing import Literal

def choose_next(state: dict) -> Literal["retrieve", "answer", "clarify"]:
    intent = state.get("intent")
    if intent == "needs_sources":
        return "retrieve"
    if intent == "simple":
        return "answer"
    return "clarify"

builder.add_conditional_edges(
    "classify",
    choose_next,
    {"retrieve": "retrieve", "answer": "answer", "clarify": "clarify"},
)
```

The fallback to clarification is only appropriate if it is safe for the task. For a money movement or an access-control decision, an unknown result should normally stop and request a trusted decision rather than proceeding through a permissive route. Routing policy belongs in application code and should be tested with values not generated by the happy-path model.

## Branches, fan-out, and joins

A router can select more than one destination. Selected nodes are scheduled in the next super-step, which allows parallel branches. This can help when multiple independent sources or checks are needed. A reducer is required when those parallel nodes write the same state channel and their updates should be combined. A later join step can consume the merged state. Avoid assuming a branch writes before another branch just because its node was declared first.

For a variable number of similar tasks, use `Send`: each `Send` names a target node and supplies an input for that particular worker invocation. This is useful for map-reduce tasks where the number of items is only known at runtime. A normal conditional edge picks nodes in the fixed graph topology; `Send` can invoke the same worker once per item with distinct inputs. If every worker writes to a shared list, its reducer should handle the updates deterministically and the downstream collector should tolerate missing or duplicate results.

A join is also a business decision. If the answer requires all three sources, a missing branch result should be an error or an explicit partial answer, not an implicit success. Track expected and completed work, or use graph structure that ensures the collector is scheduled only after the intended branches. Write tests for zero, one, and many fan-out items, and for the failure of one worker.

## Complete worked graph: classify, retrieve, or clarify

This complete graph illustrates a classifier and explicit routing with two terminal paths. Its classifier is simple deterministic Python for reproducibility; replace it with a model only after keeping the output contract constrained. `answer` is a stub for an actual retrieval component, and the graph does not claim that a text search proves factual correctness.

```python
from typing import Literal
from typing_extensions import TypedDict
from langgraph.graph import END, START, StateGraph

class RouteState(TypedDict):
    question: str
    intent: str
    result: str

def classify(state: RouteState) -> dict:
    text = state["question"].lower()
    if "source" in text or "evidence" in text:
        intent = "needs_sources"
    elif len(text.split()) < 5:
        intent = "unclear"
    else:
        intent = "simple"
    return {"intent": intent}

def retrieve(state: RouteState) -> dict:
    return {"result": f"Retrieval would run for: {state['question']}"}

def answer(state: RouteState) -> dict:
    return {"result": f"Direct-answer path selected for: {state['question']}"}

def clarify(state: RouteState) -> dict:
    return {"result": "Please provide more context so the request can be routed safely."}

def route(state: RouteState) -> Literal["retrieve", "answer", "clarify"]:
    routes = {"needs_sources": "retrieve", "simple": "answer", "unclear": "clarify"}
    return routes.get(state["intent"], "clarify")  # safe fallback for unexpected labels

builder = StateGraph(RouteState)
for name, fn in [("classify", classify), ("retrieve", retrieve), ("answer", answer), ("clarify", clarify)]:
    builder.add_node(name, fn)
builder.add_edge(START, "classify")
builder.add_conditional_edges(
    "classify", route,
    {"retrieve": "retrieve", "answer": "answer", "clarify": "clarify"},
)
for terminal in ("retrieve", "answer", "clarify"):
    builder.add_edge(terminal, END)
graph = builder.compile()

result = graph.invoke({"question": "Find evidence for the claim", "intent": "", "result": ""})
assert result["intent"] == "needs_sources"
assert result["result"].startswith("Retrieval would run")
```

There are three important contracts. First, only `classify` writes the `intent` field. Second, the router handles unexpected values and chooses a conservative path. Third, every branch ends. Without explicit terminal edges or other outgoing transitions, the workflow can halt before the intended result is produced. In a real application, the retrieval node should return structured documents and provenance, while the answer node should distinguish a grounded response from an unsupported one.

## When to use `Command`

`Command` can return an update and a destination in one node result:

```python
from typing import Literal
from langgraph.types import Command

def inspect(state) -> Command[Literal["approve", "stop"]]:
    if state["valid"]:
        return Command(update={"status": "ready"}, goto="approve")
    return Command(update={"status": "invalid"}, goto="stop")
```

This is useful when validation and routing are one semantic operation. For route-only logic, a conditional edge usually makes the topology clearer. If using `Command[Literal[...]]`, annotate possible destinations so the graph is inspectable. A `Command` from a node can also navigate to a parent graph from a subgraph with the appropriate parent target, but that is a more advanced boundary choice.

## Common mistakes

- **A router returns a node that is not registered.** Keep a finite route map and test every possible label.
- **The wrong default is permissive.** Unknown labels should not trigger high-impact actions.
- **A conditional route and static edge both leave a node.** They can both schedule work; choose one control-flow mechanism per step.
- **Parallel branches race to overwrite a field.** Add a reducer or give each branch a distinct channel.
- **Fan-out results are treated as ordered or complete without a contract.** Carry stable IDs and define failure behavior.

## Production notes

A routing function should be cheap enough to inspect and deterministic enough to reproduce. Record the selected label, but avoid logging sensitive raw input unless retention and access controls allow it. For workflows driven by a model, log the validated route separately from the raw response. Test the router with missing values, unexpected labels, and contradictory state, then test the full graph to ensure every path reaches either a valid terminal result or a deliberate stop.
