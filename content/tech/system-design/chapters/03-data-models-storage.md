# Data Models, Access Patterns and Storage Selection

The most consequential decision in a design is not which database product to use — it is which
access patterns the system must serve, at what volume, and how stale the answer may be. Storage
follows from that list. Teams that pick the engine first spend the next two years working around
the choice.

## Write the access patterns down

A useful access-pattern table has five columns: the operation, its frequency, the latency target,
the consistency requirement, and the shape of the result (single row, page of rows, aggregate).
For the running example:

| Access pattern | Frequency | Latency | Consistency | Shape |
|---|---|---|---|---|
| Get user profile by id | 30,000/s | p95 20 ms | read-your-writes | one row |
| Update profile | 400/s | p95 100 ms | strong | one row |
| Append event | 4,860/s peak | p99 200 ms | durable, ordered per user | append-only |
| Last 50 events for a user | 2,000/s | p95 80 ms | bounded staleness 1 s | page, newest first |
| Events by country, last 90 days | 40/day | minutes | eventual | scan and aggregate |
| Free-text search over profiles | 300/s | p95 150 ms | eventual | ranked list |

That table already decides most of the architecture. Profile reads are point lookups at high
volume — a cache in front of a key-value or relational store. Event appends are immutable and
ordered per key — a partitioned log. The 90-day aggregate is a scan over billions of rows — a
columnar store, never the transactional database. Search needs an inverted index, which is a
different data structure entirely.

## The engine families and what each is bad at

| Family | Good at | Fails at |
|---|---|---|
| Relational (PostgreSQL, MySQL) | Transactions, joins, constraints, ad-hoc queries | Wide scans over billions of rows; write throughput beyond one primary |
| Key-value (Redis, DynamoDB) | Point lookups at very high QPS, predictable latency | Multi-entity queries, aggregation, anything unplanned |
| Document (MongoDB) | Nested aggregates fetched as a unit, flexible schema | Cross-document joins, multi-document transactions at scale |
| Wide-column (Cassandra, Bigtable) | Huge write volume keyed by partition, time-series access | Ad-hoc queries, aggregation without a pre-built table |
| Search (OpenSearch, Elasticsearch) | Relevance, fuzzy matching, faceting | Being a system of record; consistency |
| Columnar files/warehouse (Parquet, Snowflake, BigQuery) | Scans and aggregation over huge history, cheap storage | Point updates, high-frequency single-row reads |

The right question is never "which is fastest" but "which failure mode can this workload
tolerate". A key-value store that loses the ability to answer an unplanned query is fine for
session tokens and wrong for invoices.

## Worked example: one company, two models

A 300 million-user product with a 140 GB/day event stream needs both, and the numbers say why.

**Profiles.** 300 million rows at 1 KB each is 300 GB — small enough for a single Postgres
primary, with a read replica for the 30,000/s read path and a Redis cache for the hot 20%.
Sharding is unnecessary at this size, and saying so is a stronger answer than sharding
pre-emptively: 300 GB ÷ 16 shards = 18.75 GB per shard, which saves nothing and costs operational
complexity.

**Events.** 140 million rows per day grow without bound. A relational table would be 51 TB/year
raw, with an index larger than most instances' RAM. The model is append-only, ordered per user,
and queried by time range and by scan — which is exactly the shape of a partitioned log plus
Parquet on object storage.

**Search.** Two million profiles need fuzzy matching on name and company. Neither Postgres `LIKE`
nor a key-value store serves that; an inverted index does, fed asynchronously from the profile
change stream. Its staleness of a few seconds is acceptable because search results are advisory.

## Schema design: normalise the writes, denormalise the reads

Third normal form exists to make one fact live in one place, so an update cannot leave two
copies disagreeing. That is the right default for the transactional system of record. It is the
wrong default for a read path that assembles a page from nine tables on every request.

The resolution is a boundary: normalised behind the write API, denormalised in materialised
read models built from the change stream. A `user_feed` table that repeats the author's display
name is correct if the feed is rebuilt when the name changes — and a bug if it is not.

```python
from dataclasses import dataclass
from datetime import datetime

@dataclass(frozen=True)
class Event:
    event_id: str        # UUIDv7 — time-sortable, generated by the client
    user_id: int         # partition key: all events for a user land together
    event_type: str
    occurred_at: datetime
    payload: dict

# Parquet layout: partition by event_date, cluster by user_id within the file
# path: s3://lake/events/event_date=2026-11-21/part-00017.parquet
```

Two details carry most of the value. The identifier is generated by the producer, so a retry
carries the same id and the consumer can deduplicate. The partition key is `user_id`, because
every high-volume read is "this user's events"; a key of `event_id` would scatter a user's events
across every partition and turn one read into a fan-out.

## Keys, indexes and the cost of a second access path

In a relational store, an index is a second copy of the data sorted differently. It makes one
read fast and every write slightly slower, and it consumes memory that would otherwise cache
rows. A covering index on `(user_id, occurred_at DESC) INCLUDE (event_type)` serves the paging
query without touching the table, at roughly the width of those columns per row.

In a wide-column store there are no secondary indexes worth relying on: you build a table per
query, and each table is a write amplification. Three query tables means three writes per event.
That is a legitimate trade, but it must be counted — at 4,860 events/s it is 14,580 writes/s.

In a columnar store the analogue of an index is **partitioning and clustering**: partition by
date so retention is a metadata operation and queries prune, cluster by the high-cardinality
filter column so min/max statistics stay selective.

## Schema evolution

Every model above will change. The rules that keep changes deployable:

- **Add fields, never repurpose them.** A column that meant "price in USD" and now means "price
  in cents" is a data corruption bug with a migration attached.
- **Make new fields optional with a defined default**, and let readers tolerate absence.
- **Version the contract at the boundary** — Avro or Protobuf with a schema registry for streams,
  additive changes only for tables, and a compatibility check in CI.
- **Keep the raw layer immutable.** If the parse was wrong, replay from raw rather than
  reconstructing from a lossy derived table.

## Common mistakes

- **Choosing storage by benchmark.** A benchmark measures someone else's workload; your access
  patterns are the input, not the leaderboard.
- **Polyglot persistence by fashion.** Six engines means six backup, monitoring and upgrade
  stories, usually for one team.
- **Storing blobs in the database.** A 5 MB image in a row turns every backup and replica into an
  object-storage bill with worse tooling.
- **Designing the read model before the write model.** You cannot know what to denormalise until
  you know what the source of truth is.
- **Ignoring delete and retention.** GDPR deletion across a log, a lake and a search index is a
  design requirement, not an afterthought.

## Production notes

Keep the access-pattern table in the repository and update it when a new query ships. It is the
artifact that tells the next engineer why the schema looks the way it does, and it is the first
thing to re-read when a table outgrows its engine.
