# Vault, Secrets and Least Privilege

Automation often needs credentials: SSH keys, API tokens, database passwords, certificates or encryption keys. A playbook that prints, commits or broadly distributes those values can turn routine deployment into a security incident. Ansible Vault encrypts data at rest in files or variables, but it is only one component of a secrets design. Protecting the vault password, constraining access, minimizing exposure in task output and rotating credentials remain necessary.

## Ansible Vault basics

Vault can encrypt an entire file or a single value. `ansible-vault create group_vars/production/vault.yml` creates an encrypted file; `ansible-vault encrypt` encrypts an existing file; `ansible-vault edit` opens it for controlled editing; `ansible-vault view` displays plaintext to an authorized operator; and `ansible-vault encrypt_string` encrypts a value for inline use. Decryption requires a vault password or configured vault identity. Do not put that password in the same repository as the ciphertext.

```yaml
# group_vars/production/vault.yml (encrypted at rest)
db_password: !vault |
  $ANSIBLE_VAULT;1.1;AES256
  ... encrypted payload ...
```

In a real file, the encrypted payload is generated by the command; never hand-edit its format. Use `--ask-vault-pass` for an interactive run, or a protected vault password file or credential integration in CI. Restrict access to that secret source and avoid exposing it in process arguments, logs or shell history. A vault ID label can distinguish environments or secret domains, for example `--vault-id production@prompt`; labels help select credentials but do not replace access controls.

Encrypting a value protects it in the repository, not after it is decrypted for task execution. Tasks can expose values through debug output, diffs, callback plugins, exception messages, temporary files or downstream application configuration. Mark sensitive tasks `no_log: true` where appropriate, avoid templating secrets into debug strings, and set restrictive filesystem permissions on files that must hold a secret. Also protect backups, artifacts and controller workspace storage.

## Least privilege applies to both ends

Use a dedicated automation identity with only the access required for the playbook. On Linux, SSH as a non-root account and elevate with `become` only for tasks that need system privileges. Sudo policy should match the operational requirements rather than granting unrestricted access by default. Some module behavior requires root; others do not. Split unprivileged and privileged work when that meaningfully reduces exposure, but avoid excessive complexity.

Cloud API credentials should be scoped to the resources and actions required, ideally short-lived and issued to the execution environment at job time. Do not store long-lived cloud credentials in role defaults, ordinary inventory, repository history or container images. A CI job that can deploy production should have explicit approval and environment isolation; forks or untrusted pull requests must not receive deployment secrets.

Use separate credentials for dev, staging and production where possible. Restrict which operators and pipelines can request each credential. Vault encryption is not authorization by itself: anyone with the ciphertext and the vault password can decrypt it. If a credential is committed accidentally, deleting the file in a later commit does not erase repository history; revoke and rotate the credential, then assess exposure.

## Secret lifecycle and runtime handling

Secrets should be created, distributed, used and rotated through an explicit lifecycle. Avoid copying a secret into multiple plaintext variable files. Reference a managed secret system through a supported lookup or external credential mechanism if the environment supports one, and validate what runs on the controller versus the target. Ansible lookups generally execute on the controller, so a lookup does not imply that a managed host has fetched the secret itself.

When a service needs a secret in a configuration file, set owner and mode and consider whether a runtime secret mount or managed credential agent is safer than a static file. If a task changes a secret, ensure logs and diffs are suppressed and downstream restart/reload behavior is intentional. Avoid command-line arguments carrying passwords because operating-system process listings and job logs can expose them. Environment variables also have leakage risks in process environments and diagnostics; use the platform's recommended secret injection mechanism.

## Vault IDs and rotation

Vault IDs can label encrypted data and let Ansible choose among several vault secrets. They are helpful for separating environments or teams, but naming conventions and password distribution must be managed. Re-encrypting a file after rotation does not rotate the credential represented by its plaintext. Credential rotation means updating the service or provider, deploying the new value, confirming it works, and revoking the old value according to a tested sequence. Plan for rollback without restoring an already compromised credential.

A secret's classification can change as it is transformed. A Vault-encrypted file may be low risk in source control, while its decrypted value in a CI log, a remote `/etc` file, or a database dump is high risk. Identify each copy and define access and retention. Avoid using secret values as task names, loop labels, file names or resource tags because those fields are often emitted in logs. If a task needs to compare a secret, use a mechanism that does not print both values on failure. No single Ansible flag can make a broad controller or target compromise harmless; use short-lived credentials, separate environments and provider-side revocation to limit impact. Build access review and rotation into routine operations rather than waiting for an incident.
## Common mistakes

- Committing a vault password file or putting it beside encrypted data in the same accessible repository.
- Assuming Vault prevents plaintext from appearing in logs, diffs or target files.
- Using a single powerful account and `become: true` for every task by default.
- Passing secrets through command-line flags or printing registered results with debug.
- Treating a deleted Git file as removal of a leaked credential from history.
- Giving production secrets to jobs that process untrusted branches or pull requests.

## Production notes

Review how secrets move through the entire job, not only how a variable file is encrypted. The controller may load values into memory, pass them to a module, render them into a remote file and emit task metadata through a callback. Restrict controller access, job artifacts and target file permissions accordingly. Do not assume that an encrypted repository makes it acceptable to grant every engineer decryption access; separate duties and production approvals where the risk warrants it. Maintain a rotation runbook that covers dependent services, staggered acceptance of old and new credentials, and recovery if only part of the fleet updates. Audit secret access and job invocation. After rotation, search logs and artifacts for accidental copies and apply retention or deletion controls, but still consider any copied value compromised until revoked.

Use Vault or an external secrets manager for encrypted-at-rest inputs, and a separate protected mechanism for decryption credentials. Restrict both controller and target privileges, set file permissions explicitly, suppress sensitive task output, and audit who can trigger production jobs. Test rotation and recovery before an incident. After any suspected exposure, revoke or rotate the credential first; repository cleanup alone is insufficient.
